# LQA Checker

遊戲在地化品質檢查工具。用螢幕 OCR 把遊戲實際顯示的對白抓下來，再跟翻譯文本對答案，
找出未套用翻譯、超框截斷、文字不一致、順序錯誤、缺句與發話者錯誤。

檢查方向是單向的：**使用者給的翻譯文本是正確答案，遊戲畫面是待檢查的對象。**

目標環境：Windows + 雷電模擬器，目標語言先做英文。

## 發佈一個版本

版本號規則見 `CHANGELOG.md`：最前面是大型更新或翻修，中間是新功能或
較多修復，最後是小修。

```
# 1. 改版本號（唯一的來源）
#    lqa/__init__.py 的 __version__

# 2. 打標籤。訊息寫成「版本號 一句話」，發佈說明會拿這句當摘要
git tag -a v1.0.1 -m "1.0.1 修正某某"

# 3. 更新版本紀錄並打包
.venv/Scripts/python.exe tools/make_changelog.py
.venv/Scripts/python.exe tools/build_app.py
.venv/Scripts/python.exe tools/build_installer.py

# 4. 產生要貼到 GitHub 的發佈說明
.venv/Scripts/python.exe tools/release_notes.py

# 5. 推上去
git push && git push --tags
```

在 GitHub 上 Releases -> Draft a new release，標籤下拉選單裡選剛才那個，
說明貼 `dist/release-notes-<版本>.md` 的內容，附件上傳 `dist/` 裡的
`LQA-Checker-<版本>-setup.exe` 與 `LQA-Checker-<版本>-portable.zip`。

發佈說明是從 commit 訊息的內文產生的 —— 那裡本來就寫了「為什麼這樣改」，
正是看發佈說明的人想知道的。所以 commit 訊息值得好好寫。

要補發舊版本的說明：`tools/release_notes.py v0.16.0`。

## 打包給同事用

同事不需要裝 Python 或任何東西，執行檔就是完整的。

```
.venv/Scripts/python.exe tools/build_app.py         # 資料夾版 + zip 版
.venv/Scripts/python.exe tools/build_installer.py   # 安裝精靈（需要 Inno Setup）
```

產出在 `dist/`：

| 檔案 | 用途 |
|---|---|
| `LQA Checker/` | 資料夾版，直接執行裡面的 exe |
| `LQA-Checker-portable.zip` | 解壓即用，不必安裝 |
| `LQA-Checker-setup.exe` | 安裝精靈，會建捷徑、可從「應用程式與功能」移除 |

裝不起來或開不起來時，先跑自我檢查：

```
"LQA Checker.exe" --self-test
```

它會在同一個資料夾寫出 `self-test.txt`，裡面有 Qt、辨識模型、引擎的狀態。
（安裝版在開始功能表也有「檢查安裝是否完整」。）

設定與資料都放在執行檔旁邊的 `config/`、`projects/`、`logs/`，
整個資料夾搬到別台機器就能接著用。重新安裝不會蓋掉已經校準好的 `config/`，
移除也不會刪掉 `projects/`。

## 為什麼分成兩個階段

```
階段一  shoot     玩遊戲，看到句子顯示完整就按 F9 拍一張（只存圖）
階段二  read      離線把截圖辨識成文字
階段三  compare   把整段對到翻譯文本，分類並輸出報告
```

拆成三段的理由：

- **順序與缺句必須整段跑完才判斷得出來**，所以比對不能邊玩邊做
- **遊戲不會告訴你「這句顯示完了」**。試過等畫面靜止、看變動比例、
  看筆畫消失量三種自動判準，每一種都在某類句子上失敗 ——
  短句沒有靜止期、刪節號的停頓偽裝成結束。使用者的眼睛有這個訊號，程式沒有，
  所以由使用者按鍵決定
- **遊玩當下只存圖不辨識**，按鍵幾乎沒有延遲，也不需要持續輪詢擷取，
  模擬器完全不受影響。參數調整後可以重跑辨識與比對，不必重玩一次

## 安裝

在**專案資料夾**裡執行（就是這個 README 所在的資料夾）：

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m pip install -r requirements-ocr.txt
```

直接指定 `.venv/Scripts/python.exe` 就不必先 activate，PowerShell 與 Git Bash 都通。

只要跑比對（例如重新分析已錄好的 session）的話，裝 `requirements.txt` 就夠了。
OCR 那包約 100MB，首次執行時還會再下載一次模型檔。

注意 opencv 必須裝**完整版** `opencv-python`，不能裝 `opencv-python-headless`。
headless 版沒有 GUI，`calibrate` 的框選視窗與遮罩預覽會開不起來。

## 檔案放哪

```
LQA/
  config/
    profile.json      calibrate 產生，不要手動編（可手動微調門檻）
    speakers.csv      發話者中英對照表，自己建
                      xlsx 第一欄中文第二欄英文；txt / md / csv 用逗號分開
                      範例見 speakers.example.csv 與 speakers.example.txt
  scripts/
    你的翻譯文本.xlsx   從 Google 試算表下載成 xlsx 放這裡
  sessions/           截圖與辨識結果，程式自動建立
  reports/            比對報告，程式自動建立
```

`config/profile.json`、`config/speakers.csv`、`scripts/`、`sessions/`、`reports/`
以及所有 `.xlsx` / `.csv` 都已經在 `.gitignore` 裡，**遊戲文本不會被推上 GitHub**。

路徑其實可以放任何地方，上面只是建議；實際位置在指令用 `--script` 等參數指定即可。

## 使用流程

### 1. 校準（每個解析度做一次）

先開好雷電模擬器並讓遊戲停在有對白的畫面，然後：

```bash
python -m lqa windows
```

找出雷電視窗的標題，接著框選對白框與姓名框：

```bash
python -m lqa calibrate --window 雷電模擬器 --profile config/profile.json
```

會依序框選**對白框**與**姓名框**，然後**兩個框各自調一次遮罩參數**。
分開調是必要的：對白通常是 `#fefefe`，而發話者可能是 `#fefefe` 也可能是 `#5dbcfe`。

**這一步是整套工具最關鍵的地方。** 程式不是直接比對原始像素，而是先把 ROI
轉成「只剩文字筆畫」的遮罩，再拿遮罩做變動偵測與 OCR。參數調不對的話，
變動偵測會被背景誤觸發，或是變色字被整段濾掉導致 OCR 缺字。

```
1 ~ 5       切換取字方式 (value / colorkey / otsu / adaptive / bright)
[ / ]       調整門檻（value/bright 調亮度門檻，colorkey 調容許色距）
i           反相（淺底深字時開）
c           開關 CLAHE（只對 otsu/adaptive 有意義）
- / =       調整 OCR 放大倍率
s           存檔並進入下一步    q / Esc  放棄離開
```

預覽視窗上半部是原圖、下半部是遮罩，可以直接對照哪些字被吃掉了。
目標是**下半部只剩文字筆畫、背景全黑**，且每個字都在。

如果想讓 colorkey 模式預先帶入文本用過的顏色，加上 `--script`：

```bash
.venv/Scripts/python.exe -m lqa calibrate --window 雷電模擬器 --profile config/profile.json --script scripts/你的文本.xlsx
```

### 2. 診斷（正式開始前一定要跑）

校準存檔不代表參數是對的。截圖與辨識都不會告訴你「遮罩把字吃掉了」或
「ROI 框到背景了」，但 `probe` 會。讓遊戲停在一句有對白的畫面，然後：

```bash
.venv/Scripts/python.exe -m lqa probe --profile config/profile.json
```

它會抓一張畫面，印出每個 ROI 的遮罩覆蓋率與 OCR 實際讀到的內容，
並把原圖與遮罩存成 PNG 到 `debug/`。

判斷標準：

- **OCR 讀到的內容要和畫面上的字一字不差**（發話者的 `(11201)` 會保留，那正常，比對時才剝）
- 覆蓋率大致落在 3% ~ 12%。低於 `min_text_pixels` 或高於 15% 會出警告
- 打開 `*_遮罩.png`：應該只剩文字筆畫、背景全黑，而且**每個字都在**

有問題時的對策：

| 症狀 | 對策 |
| --- | --- |
| 覆蓋率過高、遮罩一片白 | ROI 框到背景，重新校準框緊一點；或用 `[` `]` 把門檻調高 |
| 變色字整段不見 | 取字方式不是 `value`，重新校準時按 `1` |
| 有文字像素但 OCR 讀不出來 | `mask.upscale` 調大到 3，或 `ocr.source` 改成 `gray` |
| 多行對白順序錯亂 | 回報給我，這是 bug |

也可以直接診斷現成截圖，不必開著模擬器（截圖尺寸需與校準時一致）：

```bash
.venv/Scripts/python.exe -m lqa probe --profile config/profile.json --image 你的截圖.png
```

### 3. 截圖

正常遊玩，**看到一句顯示完整了就按 F9 拍一張**：

```bash
.venv/Scripts/python.exe -m lqa shoot --name ch1
```

| 按鍵 | 作用 |
| --- | --- |
| F9 | 截圖 |
| F10 | 取消上一張（按錯或手滑時用） |
| Ctrl+C | 結束 |

熱鍵是全域的，焦點在模擬器上也收得到，不必切回終端機。
截圖當下**不做辨識**，只存原圖，所以按下去幾乎沒有延遲，
而且不需要持續輪詢擷取畫面，模擬器完全不受影響。

多按幾張沒關係 —— 重複與半句會在下一步自動合併。

### 4. 辨識

```bash
.venv/Scripts/python.exe -m lqa read sessions/20260914_143000_ch1
```

會逐張 OCR 並寫出 `lines.jsonl`，順便合併兩種多餘的截圖：

- **重複**：連按兩次或畫面沒推進，文字相同就合併
- **半句**：打字中途按下，或先點一下跳過動畫再點一次推進。
  前一張的文字若是後一張的前綴，就用完整的那張取代

辨識用的是截圖當下存在 `meta.json` 裡的那組設定，所以參數改了可以直接重跑，
不必重玩一次。用 `lqa show-session` 檢查結果。

一章分好幾次拍沒問題，比對時把多個 session 依序傳進去即可。

> `lqa record` 是自動偵測版本，目前**不建議使用**。
> 遊戲沒有給出「這句顯示完了」的任何訊號，只能從像素反推，
> 試過等畫面靜止、看變動比例、看筆畫消失量三種判準，
> 每一種都在某類句子上失敗。保留著之後再研究。

### 5. 比對

準備發話者中英對照表（參考 `config/speakers.example.csv`），然後：

```bash
.venv/Scripts/python.exe -m lqa compare --script scripts/你的文本.xlsx --speakers config/speakers.csv --session sessions/20260911_143000_smoke --out reports/smoke --show 10
```

輸出 `reports/smoke.xlsx`（含摘要與明細，依分類上色）與同名 `.csv`，
`--show 10` 會順便在終端機印出前 10 筆問題。

比對前可以先確認文本讀得對：

```bash
.venv/Scripts/python.exe -m lqa check-script --script scripts/你的文本.xlsx --speakers config/speakers.csv
```

## 分類定義

| 分類 | 判定方式 | 可靠度 |
| --- | --- | --- |
| 未翻譯/未套用 | 畫面出現中文字元；再拿中文原文欄反查是哪一句，報得出 ID | 高 |
| 超框 | 畫面文字是譯文的前綴，且長度明顯不足 | 高 |
| 不一致 | 同一個位置但文字對不上 | 中，需人工複核 |
| 順序不一致 | 單調對齊配不上，但交叉比對在別的位置找到 | 中高 |
| 遊戲中沒這句 | 整段跑完後，文本裡從未被對到的句子 | 中高 |
| 發話者錯誤 | 姓名框 OCR 結果與文本發話者英文名不符 | 中高 |
| 文本中無此句 | 畫面出現但文本找不到對應（額外的第七類，通常是 OCR 雜訊或漏給文本） | 低，需人工複核 |

**這份報告是「待複核清單」，不是「確定 bug 清單」。** OCR 一定有噪音，
「不一致」那一類尤其需要人眼看截圖確認。每一筆問題都有對應截圖路徑可以回查。

## 翻譯文本格式

支援 `.xlsx` / `.csv` / `.tsv`，Google 試算表可直接下載成 xlsx。

欄位靠**標題文字**辨識，不是靠欄位位置，所以欄位順序可以不同：

| 欄位 | 別名 | 必要 |
| --- | --- | --- |
| 對話ID | ID、對話編號、編號 | 是 |
| 英文翻譯 | 英文、English、EN、翻譯 | 是 |
| 名字 | 發話者、角色、speaker | 否（中文，需搭配對照表） |
| 文字對話 | 中文、原文、source | 否（用於未翻譯反查 ID） |
| 備註 | note、remark | 否（不參與比對） |

處理規則：

- 標題列會自動尋找，不必在第 1 列
- 沒有對話ID 的列（場景說明、轉場註記）自動跳過
- **列順序就是期望播放順序，對話ID 不參與排序。** 實際文本會把後加的句子
  （例如 80208118）插在 80208010 與 80208011 中間，照 ID 排會錯
- **一個活頁簿會有多個頁簽**（活動簡介、大綱、AVG1..AVG10），
  程式只認得出裝著對白的那些。有多個時要用 `--sheet` 指定，
  或用 `--sheet all` 把全部串成一條序列

## 發話者對照表

文本裡的發話者是**中文**，遊戲畫面顯示的是**英文**，所以需要一張跨檔案共用的
中英對照表把中文名換成英文名，那個英文名就是發話者檢查的正確答案。

```
文本「蘇青」 --[對照表]--> 正確答案 "Suqing"
                              vs
畫面 OCR "Suqing(11201)" --[剝除流水號]--> "Suqing"    相符
畫面 OCR "Nev(11203)"    --[剝除流水號]--> "Nev"       發話者錯誤
```

用 `lqa speakers` 可以從文本掃出所有發話者，產生只差英文名的範本：

```bash
.venv/Scripts/python.exe -m lqa speakers
```

它會掃過**所有頁簽**，寫出 `config/speakers.csv`。重跑時已填好的英文名會保留。

如果你已經有一份共用的對照表，直接用 `--speakers 路徑` 指定即可。
格式很寬鬆：支援 csv / tsv / xlsx，中英兩欄靠標題文字辨識
（中文欄認 `名字` `中文名` `角色名` `speaker` 等，英文欄認 `English` `英文名` `EN` 等），
兩欄不一定要相鄰，標題也不一定要在第 1 列；完全沒有可辨識的標題時，
會退回「第一欄中文、第二欄英文」。

**留空英文名的發話者會被跳過而不是報錯**，所以可以先跑對白比對，之後再補。

## 文字正規化

比對前兩邊都會拉到同一個基準，否則以下都會變成假 bug：

- 彎引號 `’` `“` 轉直引號、破折號 `—` `–` 統一、`…` 展開成 `...`
- 全形空白、不斷行空白、零寬字元
- 富文本標記 `<color=#FF0000>`、`[b]`
- 變數佔位符 `{playerName}`、`%s`、`%1$s`（只要求固定片段相符）
- 比對時移除所有標點，OCR 最常錯的就是標點
- OCR 固定誤判組 `l/I/1`、`O/0`、`rn/m` 折疊後取較高分

注意：**不能用「結尾是刪節號」當超框訊號**，因為專案譯文本身大量使用 `...` 結尾。
唯一可靠的訊號是前綴關係加上長度明顯不足。

## 已知限制

- 相鄰兩張截圖文字完全相同時會被當成重複而合併。劇情真的連著講兩次一樣的話時，
  會在報告中呈現為「遊戲中沒這句」，複核截圖即可確認。用 `--no-clean` 可關閉合併。
- 對話有分支選項時，工具不會知道你選了哪一條；跑不同分支請分開截圖、分開比對。
- 模擬器**不能最小化**（最小化的視窗沒有可繪製的內容）。被其他視窗蓋住沒關係。
- 目前只針對英文調校。要加日韓需要換 OCR 語言模型，並調整正規化規則。

## 擷取後端

| 後端 | 做法 | 被其他視窗蓋住 | 模擬器 CPU |
| --- | --- | --- | --- |
| `auto` | 沒被蓋用 mss，被蓋才用 PrintWindow | 抓得到 | **0.8% / 5.4%** |
| `printwindow` | 一律請視窗自己把內容畫出來 | 抓得到 | 5.4% |
| `mss` | 一律抓螢幕上那塊區域 | 抓到遮擋內容 | 0.8% |

**為什麼要混合：** PrintWindow 強迫整個視窗重繪，成本落在模擬器身上。
實測輪詢 60ms 時 dnplayer.exe 的 CPU 使用率：

| 情況 | 模擬器 CPU |
| --- | --- |
| 不擷取（基準） | 0.4% |
| PrintWindow 輪詢 | **5.4%** |
| mss 輪詢 | 0.8%（和基準沒差別） |

我們自己的行程只看到 4.4ms 對 1.8ms 的差距，看不出全貌 —— 使用者回報
「開了腳本模擬器會卡」就是這個。但 mss 被蓋住會抓到蓋在上面的東西而且**不報錯**。

所以每次擷取前先用 `WindowFromPoint` 檢查對白框有沒有被蓋住（只要十幾微秒），
沒被蓋就走便宜的路，被蓋住才付 PrintWindow 的代價。
正常使用時模擬器完全不受影響，把別的視窗拉到前面時畫面依然正確。
手動截圖模式只在按鍵當下抓一張，連這點成本都省了。

只檢查**對白框**那一塊，不是整個視窗 —— 視窗被蓋住一角但對白框沒事的話，
沒必要付那個代價。

所有後端都要求視窗是**還原**狀態。最小化的視窗 `GetClientRect` 會回出
`(-32000, -32000)` 這種垃圾座標，程式會偵測到並提示，還原後自動繼續。

## 取字方式怎麼選

對白框背景是**漸變變暗**的（不是半透明），文字則是直接疊在上面的高亮度顏色，
所以取字看亮度就夠準，不需要自適應門檻。

| method | 做法 | 適用 |
| --- | --- | --- |
| `hysteresis` | 高門檻找筆畫核心當種子，低門檻取完整筆畫，只留連通到種子的部分 | **預設，建議用這個** |
| `value` | 取 RGB 三通道最大值（等同 HSV 的 V）再砍單一門檻 | 字體單純時夠用 |
| `colorkey` | 只保留與指定顏色夠接近的像素 | 精度最高，但要先備妥完整色盤 |
| `bright` | 灰階亮度門檻 | **不建議**，見下 |
| `otsu` / `adaptive` | 自適應門檻 | 背景一複雜就會飄，留作退路 |

**為什麼需要雙門檻：** 遊戲的對白字不是均勻的純色，而是
「純白核心 → 灰白過渡 → 灰黑描邊」的結構。實測一張真實畫面的亮度分布：

| 亮度區間 | 像素數 | 是什麼 |
| --- | --- | --- |
| 240-256 | 1300 | 筆畫核心（接近純白） |
| 200-240 | 865 | 過渡 |
| 150-200 | 778 | 過渡 |
| 100-150 | 2066 | 抗鋸齒與描邊 |
| 60-100 | 11816 | 背景 |

單一門檻對這種結構本質上就不管用：門檻放高只留核心，字被挖空；
門檻放低才收得到完整筆畫，但背景也一起進來。遲滯門檻兩邊都解決 ——
核心一定過得了高門檻所以每個筆畫都有種子，過渡區過得了低門檻且與核心相連
所以筆畫完整，背景就算亮到過得了低門檻，也會因為連不到種子而被丟掉。

實測（同一張真實畫面，與正確譯文比對）：

| 設定 | 遮罩覆蓋 | 相似度 |
| --- | --- | --- |
| `value` 門檻 85 | 11.13% | 100% |
| `value` 門檻 140 | 4.08% | 99.3% |
| `hysteresis` 低 100 高 210 | **7.27%** | **100%** |

比低門檻乾淨，卻同樣一字不差。

**為什麼不用灰階亮度：** 灰階是加權平均，會嚴重低估飽和色。
文本裡的 `<color=#ff8a00>` 變色字，灰階值只有 157，用 170 門檻會被整段砍掉，
OCR 就會缺字，然後被誤報成「不一致」。而 V 值是 255，和白字 254 同一個量級。

| 顏色 | 用途 | 灰階值 | V 值 |
| --- | --- | --- | --- |
| `#fefefe` | 對白預設色 | 254 | 254 |
| `#ff8a00` | `<color>` 變色字範例 | 157 | 255 |
| `#5dbcfe` | 發話者可能用色 | 174 | 254 |

所以 `value` 一個門檻就能同時收白字、變色字與藍色發話者名，
而且**不需要事先知道文本用了哪些顏色**。

若真要用 `colorkey`，先把文本的色盤掃出來：

```bash
.venv/Scripts/python.exe -m lqa colors --script scripts/你的文本.xlsx
```

## 文字標記與發話者 ID

- `<color=#ff8a00>嗶獸</color>`、`<size=150%>` 這類標記**不會顯示在畫面上**，
  遊戲只會套用效果。比對前會把標記剝掉、保留被框住的文字，
  所以畫面讀到的純文字和文本算相符。
- 遊戲畫面的發話者後面會接內部流水號，例如 `Cyan(11201)`。
  比對前會剝掉結尾的 `(數字)`，**只有純數字才剝**，
  像 `Cyan (Disguised)` 這種有意義的括號內容會保留。

## 變動偵測的門檻怎麼定的

`stability.diff_threshold` 與 `rearm_threshold` 是「變動像素 / 文字像素量」的比例，
**不是佔 ROI 面積的比例**。在合成畫面（半透明框加會動的背景）上實測：

| 情況 | 佔 ROI 面積 | 佔文字像素量 |
| --- | --- | --- |
| 背景移動、文字不動 | 0.0001 ~ 0.0003 | 0.007 ~ 0.018 |
| 打字中的視窗累積量 | 約 0.004 | 約 0.13 |

文字只佔 ROI 面積 1% 出頭，用面積當分母會把訊號稀釋到跟背景雜訊同一個數量級，
所以改用文字量當分母，預設門檻 0.04 落在兩者中間，且不隨解析度或對白框大小改變。

另外偵測是比對「現在」與「stable_frames 幀之前」，不是只比前一幀 ——
打字打到空格時單幀變動量是 0，只比前一幀會誤判成已經穩定而錄到半句話。
`tests/test_capture_pipeline.py` 有這兩點的回歸測試。

## 逐句偵測怎麼判斷換句

**不是等畫面靜止。** 舊做法要求連續數幀遮罩不變才擷取，實測漏掉將近一半的句子，
而且漏的幾乎都是短句（`Found it.` / `!` / `(Where's Nev...?)`）——
短句打字快、使用者點得也快，那段靜止期根本不存在；
模擬器變卡時每輪迴圈更久，等於把門檻拉得更高。
刪節號造成的打字停頓又會偽裝成靜止，於是錄到半句（`Though..`）。

現在的判準利用打字機的性質：**打字只會增加筆畫，換句才會讓舊筆畫消失。**

1. 每一幀都和「目前這句看過最完整的那一幀」比較
2. 像素更多就取代它（還在打字）
3. 舊筆畫大量消失就代表換句了，把保留的那一幀吐出來

所以不需要任何靜止期。一句話只要在顯示完整之後被取樣到**一次**就會被完整記錄，
取樣再慢也只是降低取樣次數，而不是整句漏掉。
最後一句沒有下一句可以觸發，所以錄製結束時會 flush。

`show-session` 會標出「可能沒顯示完」與「只取樣 N 次」的句子 ——
那些是點太快、可能沒抓到完整狀態的。

## 同一句被記錄兩次

比例的分母是文字像素量，所以**句子越短越敏感**。實測一句短對白：

| 區域 | 遮罩像素 | 連續幀變動 |
| --- | --- | --- |
| 含頭像的左半 | 8102 | 最大 0.0014 |
| 純文字的右半 | 1029 | 最大 **0.0327** |

一千多像素的遮罩，抗鋸齒邊緣抖個三十幾像素就衝到 3.3%，逼近 0.04 的門檻。
更短的句子（例如「...Fine.」）分母更小，就會超過而被誤判成新的一句。

兩層防護：

1. `stability.min_changed_pixels`（預設 40）—— 變動要**同時**滿足比例與絕對像素量。
   小分母造成的假變動會被絕對量擋下來。
2. 錄製端比對 OCR 文字 —— 字一樣就是同一句，直接略過。
   但若中間對白框淨空過（過場、黑幕），代表劇情真的又講了一次，那種重複會保留。

錄製結束時會回報略過了幾次重複觸發。

## 專案結構

```
lqa/
  model.py              ExpectedLine / CapturedLine / Issue / Category
  hotkey.py             全域熱鍵偵測（GetAsyncKeyState 輪詢）
  config.py             profile：ROI、遮罩、穩定偵測、OCR 設定
  capture/              螢幕擷取（視窗定位、mss 後端）
  detect/               文字遮罩抽取、穩定幀偵測
  ocr/                  OCR 引擎抽象與 RapidOCR 實作
  record/               截圖、離線辨識、session 儲存
  compare/              正規化、文本讀取、序列對齊、分類、報告
  tools_calibrate.py    ROI 框選與遮罩預覽
  tools_probe.py        單張診斷：印出遮罩覆蓋率與 OCR 結果並存圖
  cli.py                命令列入口
tests/                  離線比對邏輯的測試（不需要遊戲即可跑）
```

## 測試

```bash
.venv/Scripts/python.exe -m pytest tests -q
```

涵蓋正規化、文本解析、序列對齊、六類分類、OCR 排序，
以及用合成畫面驗證的取字與穩定偵測。除了一項 OCR 整合測試之外，
全部不需要遊戲也不需要 OCR 即可執行（未裝 OCR 時該項自動略過）。

## 指令總覽

| 指令 | 用途 |
| --- | --- |
| `windows` | 列出所有視窗標題，用來找雷電的標題 |
| `calibrate` | 框選對白框與姓名框，各調一組遮罩參數 |
| `probe` | 抓一張畫面診斷 profile，正式錄製前跑 |
| `shoot` | 手動截圖：看到句子顯示完整就按 F9 |
| `read` | 把截圖離線辨識成文字 |
| `show-session` | 列出辨識出來的所有句子 |
| `record` | 自動錄製（實驗中，不建議使用） |
| `speakers` | 從文本掃出所有發話者，產生中英對照表範本 |
| `check-script` | 列出頁簽並檢查翻譯文本能不能正確解析 |
| `colors` | 掃出文本用過的所有文字顏色 |
| `compare` | 比對並輸出報告 |

每個指令都可以加 `--help` 看完整參數。
